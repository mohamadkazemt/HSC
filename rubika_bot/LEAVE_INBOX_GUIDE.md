# راهنمای کارتابل مرخصی در ربات روبیکا

## 📋 قابلیت جدید: کارتابل مرخصی

این قابلیت به کاربران امکان می‌دهد که درخواست‌های مرخصی منتظر تایید خود را در ربات روبیکا مشاهده کرده و مستقیماً از طریق ربات آن‌ها را تایید یا رد کنند.

## 🎯 کاربران هدف

این قابلیت برای دو گروه از کاربران طراحی شده است:

1. **جانشین‌ها (Replacement Persons)**: کاربرانی که به عنوان جایگزین در درخواست‌های مرخصی انتخاب شده‌اند
2. **مدیران تایید کننده (Approvers)**: مدیرانی که بر اساس `ApprovalHierarchy` باید درخواست‌های مرخصی را تایید نهایی کنند

## 🚀 نحوه استفاده

### برای کاربران

1. به ربات روبیکا متصل شوید (اگر قبلاً متصل نشده‌اید)
2. از منوی اصلی، دکمه **"📋 کارتابل مرخصی"** را انتخاب کنید
3. ربات لیست تمام درخواست‌های منتظر تایید شما را نمایش می‌دهد
4. برای هر درخواست، دو دکمه **"✅ تایید"** و **"❌ رد"** وجود دارد
5. با انتخاب دکمه مناسب، درخواست تایید یا رد می‌شود

### اطلاعات نمایش داده شده برای هر درخواست

- 👤 نام و کد پرسنلی درخواست‌دهنده
- 📌 نوع مرخصی (استحقاقی، ساعتی، استعلاجی، غیبت)
- 📅 تاریخ مرخصی
- 🕐 نوع شیفت
- 👥 نام جایگزین (فقط برای مدیران)
- 📝 توضیحات (در صورت وجود)
- ⏰ ساعات مرخصی (برای مرخصی ساعتی)

## 🔧 تغییرات فنی

### 1. تغییرات در منوی اصلی

```python
# قبل:
second_row = [('payslip', '💰 فیش حقوقی'), ('leave_request', '🏖️ مرخصی')]
third_row = [('help', '❓ راهنما'), ('disconnect', '🔓 قطع اتصال')]

# بعد:
second_row = [('payslip', '💰 فیش حقوقی'), ('leave_request', '🏖️ درخواست مرخصی')]
third_row = [('leave_inbox', '📋 کارتابل مرخصی'), ('help', '❓ راهنما')]
fourth_row = [('disconnect', '🔓 قطع اتصال')]
```

### 2. Handler جدید: `_show_leave_inbox`

این متد:
- درخواست‌های منتظر تایید کاربر را از دیتابیس دریافت می‌کند
- برای جانشین‌ها: درخواست‌های با وضعیت `pending_replacement`
- برای مدیران: درخواست‌های با وضعیت `pending_approval` که `get_required_approver()` آن‌ها با پروفایل کاربر مطابقت دارد
- هر درخواست را با دکمه‌های تایید/رد نمایش می‌دهد

### 3. فلوچارت فرآیند تایید

```
کاربر کلیک می‌کند روی "کارتابل مرخصی"
    ↓
_show_leave_inbox فراخوانی می‌شود
    ↓
Query به دیتابیس برای درخواست‌های منتظر
    ↓
برای هر درخواست:
    - ساخت پیام با جزئیات
    - اضافه کردن دکمه‌های تایید/رد
    - ارسال پیام
    ↓
کاربر کلیک می‌کند روی "تایید" یا "رد"
    ↓
_handle_leave_approval_action فراخوانی می‌شود
    ↓
بررسی دسترسی و وضعیت
    ↓
اگر تایید: _process_leave_approval
اگر رد: درخواست دلیل رد → _process_rejection_reason
    ↓
به‌روزرسانی وضعیت در دیتابیس
    ↓
ارسال نوتیفیکیشن به درخواست‌دهنده
    ↓
نمایش پیام موفقیت به کاربر
```

## 📊 Query Performance

برای بهینه‌سازی عملکرد:
- استفاده از `select_related` برای کاهش تعداد Query ها
- محدود کردن تعداد درخواست‌ها (10 برای جانشین، 20 برای مدیر)
- مرتب‌سازی بر اساس `created_at` (جدیدترین اول)

## 🔐 امنیت

- بررسی اینکه کاربر به حساب متصل است
- بررسی دسترسی در `_handle_leave_approval_action`:
  - برای جانشین: `leave.replacement_person == user.user`
  - برای مدیر: `leave.can_be_approved_by(user.user)`
- بررسی وضعیت درخواست (pending_replacement یا pending_approval)

## 🧪 تست

برای تست این قابلیت:

1. **آماده‌سازی:**
   - یک کاربر A (درخواست‌دهنده) داشته باشید
   - یک کاربر B (جانشین) داشته باشید
   - یک کاربر C (مدیر تایید کننده) داشته باشید
   - یک `ApprovalHierarchy` برای کاربر C تعریف کنید

2. **سناریوی تست برای جانشین:**
   - کاربر A یک درخواست مرخصی ثبت کند و کاربر B را به عنوان جانشین انتخاب کند
   - کاربر B به ربات روبیکا متصل شود
   - کاربر B دکمه "کارتابل مرخصی" را کلیک کند
   - بررسی کنید که درخواست کاربر A نمایش داده می‌شود
   - کاربر B درخواست را تایید کند
   - بررسی کنید که وضعیت درخواست به `pending_approval` تغییر کرده است

3. **سناریوی تست برای مدیر:**
   - ادامه سناریوی قبل (درخواست حالا در وضعیت `pending_approval` است)
   - کاربر C به ربات متصل شود
   - کاربر C دکمه "کارتابل مرخصی" را کلیک کند
   - بررسی کنید که درخواست کاربر A نمایش داده می‌شود
   - کاربر C درخواست را تایید کند
   - بررسی کنید که وضعیت درخواست به `approved` تغییر کرده است

4. **سناریوی تست رد درخواست:**
   - یک درخواست جدید ثبت کنید
   - جانشین یا مدیر دکمه "رد" را کلیک کند
   - دلیل رد را وارد کند
   - بررسی کنید که وضعیت به `rejected` تغییر کرده و دلیل ثبت شده است

## 📝 نکات مهم

1. **Rate Limiting**: بین ارسال هر پیام 0.5 ثانیه تاخیر وجود دارد تا از rate limiting جلوگیری شود
2. **Celery**: اگر Celery در دسترس نباشد، task ها به صورت synchronous اجرا می‌شوند
3. **Notifications**: هم نوتیفیکیشن وب و هم پیام ربات ارسال می‌شود
4. **Logging**: تمام عملیات تایید/رد در `WebhookLog` ثبت می‌شوند

## 🔄 فلوی کامل از ثبت درخواست تا تایید نهایی

```
[کاربر A] ثبت درخواست مرخصی
    ↓
[سیگنال] leave_request_created
    ↓
[Notification] ایجاد نوتیفیکیشن برای جانشین (کاربر B)
    ↓
[Task] send_leave_approval_request (ارسال پیام با دکمه به ربات)
    ↓
[کاربر B] مشاهده پیام در ربات یا کلیک روی "کارتابل مرخصی"
    ↓
[کاربر B] تایید درخواست
    ↓
[Handler] _process_leave_approval
    ↓
[DB] وضعیت → pending_approval
    ↓
[Notification] ایجاد نوتیفیکیشن برای مدیر (کاربر C) و درخواست‌دهنده (کاربر A)
    ↓
[Task] send_leave_approval_request (ارسال پیام با دکمه به ربات مدیر)
    ↓
[کاربر C] مشاهده پیام در ربات یا کلیک روی "کارتابل مرخصی"
    ↓
[کاربر C] تایید نهایی
    ↓
[Handler] _process_leave_approval
    ↓
[DB] وضعیت → approved, registration → True
    ↓
[Notification] ایجاد نوتیفیکیشن موفقیت برای درخواست‌دهنده (کاربر A)
```

## 🐛 رفع مشکلات رایج

### مشکل: درخواست‌ها در کارتابل نمایش داده نمی‌شوند

**راه‌حل:**
1. بررسی کنید که کاربر به ربات متصل است (`user.user` None نباشد)
2. بررسی کنید که `ApprovalHierarchy` به درستی تعریف شده است
3. برای مدیران، بررسی کنید که `get_required_approver()` پروفایل درست را برمی‌گرداند

### مشکل: خطای دسترسی هنگام تایید/رد

**راه‌حل:**
1. بررسی کنید که وضعیت درخواست درست است (pending_replacement یا pending_approval)
2. برای جانشین: بررسی کنید که `replacement_person` همان کاربر فعلی است
3. برای مدیر: بررسی کنید که `can_be_approved_by(user)` True برمی‌گرداند

### مشکل: پیام‌ها به ربات ارسال نمی‌شوند

**راه‌حل:**
1. بررسی کنید که `rubika_profile` برای کاربر وجود دارد
2. بررسی کنید که Celery در حال اجرا است (`celery -A HSCprojects worker`)
3. لاگ‌های Celery را بررسی کنید: `journalctl -u celery -f`

## 📞 پشتیبانی

در صورت بروز مشکل:
1. لاگ‌های application را بررسی کنید
2. لاگ‌های Celery را بررسی کنید
3. جدول `WebhookLog` را برای مشاهده جزئیات ارسال پیام‌ها بررسی کنید
4. از دستور `python manage.py shell` برای تست دستی query ها استفاده کنید
